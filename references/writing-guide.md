# Writing Guide: How to Create Documentation That Actually Works

This guide covers the craft of writing documentation that users will read, understand, and act on.
It draws from the best documentation teams in the industry (Stripe, Linear, Anthropic, Notion)
and applies those principles to AI-generated and human-reviewed documentation alike.

Every recommendation in this guide applies equally to content written by humans and content
generated by LLMs. The ADUMAS agents are prompted to follow these principles. Human reviewers
use this guide to evaluate and improve AI output before publication.

## 1. The Seven-Step Process

Every piece of documentation, whether written by a human or generated by the Documentation Generator
Agent, should follow this process. Steps can be compressed for minor updates; all seven steps apply
to new documents and major revisions.

### Step 1: Define your audience

Before writing a single word, answer: who is reading this, and what do they already know?

A senior administrator configuring SSO is a different reader from a first-time user trying to
upload their first file. The same feature generates completely different documentation for each.

Questions to answer before writing:

- What is this person trying to accomplish?
- What do they already know about the product?
- What do they know about the underlying technology?
- What will they do next after reading this?
- Where are they reading this (in-app, portal, PDF, mobile)?

### Step 2: Map the user journey

Identify the complete path a user takes to accomplish a goal. Documentation should map to
the journey, not to the product's internal structure.

A user does not think: "I need to configure the authentication module." They think:
"I need to let my team log in with their Google accounts."

Map the journey from the user's goal to the confirmed outcome. Every step in that journey
needs documentation coverage. Gaps in the journey map become gaps in the documentation.

### Step 3: Plan the structure

Decide on document type, sections, and depth before writing. Use the document type reference
in Section 11 to select the right format. Outline sections using descriptive headings before
filling in content.

A good outline for a task-based guide:

```
# How to [Accomplish Goal]

## Overview
## Before You Begin (prerequisites)
## Step 1: [First action]
## Step 2: [Second action]
## Step 3: [Third action]
## Expected Result
## Troubleshooting
## Related Topics
```

### Step 4: Write task-oriented content

Every section should help the user do something. Describe what to do, not what things are.

See Section 5 for the full task-oriented writing template.

### Step 5: Make it searchable and navigable

Users arrive at documentation with a specific question. They do not read linearly.
Make it easy to scan, jump, and find.

See Section 6 for the full searchability and navigation guide.

### Step 6: Test with real users

Documentation that has never been tested with a real user is a first draft, not a finished
product. See Section 7 for the full testing protocol.

### Step 7: Publish, maintain, and iterate

Documentation is not done when it is published. It is done when it is no longer needed.
See Section 8 for the maintenance lifecycle.

## 2. Define Your Audience

### Persona tiers

Define at least two audience tiers for any product with multiple user roles:

**End user:** Interacts with the product to accomplish a personal or work goal. Wants to know
how to do things. Does not want to know how the product works internally. Reads Getting Started
guides and How-To articles.

**Administrator / power user:** Configures the product for others. Needs to understand options,
defaults, limits, and consequences of choices. Reads Admin Guides and Reference documentation.

**Developer / technical integrator:** Connects the product to other systems. Needs API reference,
authentication details, error codes, and code examples. Reads API Reference and Integration Guides.

### Audience signals to watch for in commits

The Commit Intelligence Agent should tag documentation by audience based on what changed:

- Changes to UI flows, button labels, or onboarding paths: end user documentation
- Changes to settings pages, permissions, or billing: administrator documentation
- Changes to API endpoints, response shapes, auth schemes, or webhooks: developer documentation
- Changes to internal architecture, database schemas, or caching: internal documentation only

### Writing for multiple audiences simultaneously

Do not write one document for two audiences. Split into separate sections or separate documents.

If a topic genuinely needs both: write the end-user task first (plain language, steps, outcome),
then add a "For Administrators" or "Advanced" section below it. Never mix the two in the same paragraph.

## 3. Map the User Journey

### The journey map template

For each major feature, map the journey before writing documentation:

```
Goal: What the user is trying to accomplish
Entry point: How they found this feature (search, UI, referral)
Prerequisites: What must be true before they start
Steps: Ordered list of actions (user perspective, not system perspective)
Decision points: Where the user might make a choice that affects the path
Expected outcome: What they see when they succeed
Common failure modes: What goes wrong and why
Next step: What they will do immediately after
```

### Using journey maps to find documentation gaps

Compare your journey map against existing documentation. Every step that has no documentation
is a gap. Every decision point that is not explained is a support ticket waiting to happen.

For ADUMAS: the Codebase Analyst Agent should build journey maps by reading API call sequences
and UI navigation flows. Gaps in the journey map should trigger the Quality Agent to flag
missing documentation coverage.

## 4. Plan the Structure

### Heading hierarchy

Use headings to tell a scanning user what they will find in each section. A user reading only
the headings should understand the document's full scope.

Rules for headings:

- H1: Document title only. One per page.
- H2: Major sections. Each H2 should be independently meaningful.
- H3: Subsections. Use when a major section has more than three components.
- H4 and below: Avoid. If you need H4, the section is too complex and should be split.

### Heading style

Write headings as actions or questions when possible:

| Weak heading | Strong heading |
|---|---|
| Authentication | How to authenticate with the API |
| Export | Export your data as CSV or JSON |
| Error codes | What each error code means |
| Settings | Configure your notification preferences |
| Billing | Manage your subscription and billing |

### Section length

Sections should contain one idea. If a section covers two ideas, it should be two sections.

A section with more than 400 words is a signal to review whether it should be split.
A section with fewer than 50 words is a signal to ask whether it should be merged
with the section above or below.

## 5. Write Task-Oriented Content

### The task-oriented template

Every procedural document follows this structure:

```
## [Action verb] + [goal]

[One-sentence context: what this helps the user do and why it matters]

### Before you begin

- [Prerequisite 1]
- [Prerequisite 2]

### Steps

1. [Specific action. Include where to click, what to type, what to select.]
2. [Next action. Each step is one action only.]
3. [Continue until goal is reached.]

### What you should see

[Describe the expected outcome. What changes on screen? What confirmation appears?
What email arrives? What can the user do now that they could not do before?]

### Troubleshooting

**[Symptom]:** [Cause and fix]
**[Symptom]:** [Cause and fix]

### Next steps

- [Related task the user will likely want to do next]
- [Related topic for more context]
```

### Step writing rules

Each numbered step should contain exactly one action. If a step contains "and," it is
probably two steps.

Write steps in the imperative: "Click Save" not "You should click Save" or "The user clicks Save."

Be specific. "Configure the settings" is not a step. "In the Settings panel, set the
Timeout field to 30" is a step.

Include the result of each step when the result is not obvious:

- Good: "Click **Publish**. The page status changes from Draft to Live."
- Poor: "Click **Publish**."

### Outcome statements

Every procedure must end with an outcome statement. The user needs to know what success
looks like. The outcome statement answers: "How do I know it worked?"

Format: "You have now [achieved goal]. You can [next capability unlocked]."

Example: "You have now connected your Slack workspace. The ADUMAS system will send a
notification to your chosen channel whenever new documentation is published."

## 6. Make It Searchable and Navigable

### Search-optimized headings

Users search for their symptoms, not for feature names. Write headings that match
the words a confused user would type into a search box.

Ask: "If a user did not know what this feature was called, what would they search for?"

| Feature-named heading | Search-optimized heading |
|---|---|
| OAuth 2.0 Configuration | Connect your identity provider for single sign-on |
| Webhook Payload Schema | What data does each webhook event send? |
| Rate Limiting | Why am I getting 429 errors? |
| Semantic Versioning | How documentation versions are numbered |
| Documentation Staleness Detection | Get alerts when docs fall out of date |

### Table of contents

Add a table of contents to any document with more than four H2 sections. The TOC should
be at the top of the page, below the introduction, using anchor links.

Format:

```markdown
## In this guide

- [Step 1: Connect your repository](#step-1-connect-your-repository)
- [Step 2: Configure the agent](#step-2-configure-the-agent)
- [Step 3: Run your first generation](#step-3-run-your-first-generation)
- [Troubleshooting](#troubleshooting)
```

### Scannable formatting

Use formatting to help users find the information they need without reading every word:

- **Bold** key terms on first use and whenever they appear in a step the user must take
- Use numbered lists for sequences where order matters
- Use bullet lists for options, features, or items where order does not matter
- Use tables for comparisons, option matrices, and reference data
- Use code blocks for any text the user must type exactly
- Use callout blocks (Note, Warning, Tip) for important asides

Do not bold for decoration. Bold means "this is the most important thing on this line."

### Navigation between documents

Every document should have a "Related topics" or "Next steps" section at the end.
This is not optional. Users who finish reading a document need a path forward.

Cross-linking rules:

- Link to the most specific document, not the parent section
- Use the document title as the link text, not "click here" or "this page"
- When referencing a concept introduced elsewhere, link on first use only
- Check that cross-links are valid before publishing (the Quality Agent validates this automatically)

## 7. Test with Real Users

### Why documentation testing matters

Documentation that has never been tested with a real user contains invisible gaps.
The writer knows the product. Users do not. What is obvious to the writer is invisible
to the user.

Testing is not editing. Testing is watching a real user try to follow the documentation
and observing where they get stuck, confused, or wrong.

### The documentation testing protocol

**Participants:** Select 2-3 users who match the target persona. Do not use engineers
or product managers for end-user documentation testing. Do not use non-technical users
for developer documentation testing.

**Method:** Give the user the documentation and a goal ("Using only this documentation,
set up X"). Do not answer questions. Do not explain. Observe and take notes.

**What to watch for:**

- Where does the user pause or re-read?
- Where does the user say "I'm not sure what this means"?
- Where does the user take a different action than the steps describe?
- Where does the user give up?
- Where does the user succeed without the documentation (meaning the doc is unnecessary)?

**Output:** A list of gaps, ambiguities, and fixes. Update the documentation. Retest if
the changes are significant.

### Remote testing option

For async testing, use this format:

1. Share the documentation link with 3-5 users in the target persona
2. Ask them to complete a specific task using only the documentation
3. Ask them to mark any step where they were uncertain or confused
4. Collect the marked steps and fix the most commonly flagged issues

### What AI-generated documentation is tested on

The Documentation Generator Agent produces content that passes an automated quality
gate (completeness, structure, reading level, link validity). This is not the same as
user testing.

Human reviewers should apply the testing protocol to new documentation categories.
Once a documentation type is validated, the agent's output for similar content can
be approved with lighter review.

## 8. Publish, Maintain, and Iterate

### The publication checklist

Before any documentation is published:

- [ ] Audience is clearly defined and the content is written for that audience only
- [ ] Headings are descriptive and search-optimized
- [ ] Every procedure has numbered steps and an outcome statement
- [ ] Prerequisites are listed
- [ ] Cross-links are valid
- [ ] Screenshots are current (if included)
- [ ] Content has been reviewed by at least one human
- [ ] Glossary terms are consistent with the product glossary
- [ ] No em dashes in the content
- [ ] Plain language review: no unexplained jargon, sentences under 25 words
- [ ] Table of contents present (for documents with more than 4 sections)

### The maintenance lifecycle

Documentation is never done. After publication:

**After every product release:** Check whether documentation needs to update. The Commit
Intelligence Agent surfaces documentation candidates automatically. A human reviewer
confirms whether changes require documentation updates.

**Monthly:** Run a search gap analysis. What are users searching for but not finding?
What searches return no results? These are documentation gaps to fill.

**Quarterly:** Review documentation staleness scores. Documents flagged as stale should
be reviewed, updated, or retired. Track the correlation between stale documentation
and support tickets.

**Annually:** Run a full documentation audit. Identify content that is no longer relevant,
content that duplicates other content, and gaps in coverage for the current product.

### Versioning documentation

Documentation versions should track product versions. Use semantic versioning:

- **Major version (1.0 to 2.0):** Breaking changes visible to users. Architecture changes,
  removed features, fundamentally new workflows. Requires new documentation sections or
  full rewrites. Announce explicitly.

- **Minor version (1.0 to 1.1):** New features or significant enhancements. Requires
  new pages or new sections. Add release notes entry.

- **Patch version (1.0.0 to 1.0.1):** Bug fixes, UI label changes, minor clarifications.
  Update in place. Optional release notes entry.

### When to retire documentation

Retire documentation when:

- The feature it covers has been removed
- The documentation covers a deprecated workflow with a modern replacement
- The content is fully absorbed into another, more complete document

When retiring: replace with a redirect or a short note pointing to the replacement.
Do not delete without leaving a trail.

### Format considerations: online vs offline

| Consideration | Online (Markdown portal, Notion) | Offline (PDF, DOCX) |
|---|---|---|
| Searchability | Full text search, cross-links work | No search; relies on TOC |
| Maintenance | Update once; all users see current version | Stale copies persist after updates |
| Analytics | Track page views, search queries, bounce | No usage data |
| Interactivity | Code copy buttons, collapsible sections | None |
| Accessibility | Screen reader compatible with semantic HTML | Depends on PDF tagging |
| Use case | Default for all documentation | Compliance exports, offline access, formal delivery |

**Rule:** Markdown is always the source of truth. PDF and DOCX are rendered outputs.
Never write documentation natively in PDF or DOCX.

## 9. Plain Language Principles

Plain language does not mean simple. It means precise, efficient, and free of
unnecessary complexity.

### Core rules

**Use everyday words when technical terms are not required.**

| Jargon or complex | Plain language |
|---|---|
| Utilize | Use |
| Implement | Set up, build, add |
| Instantiate | Create, start |
| Leverage | Use |
| Facilitate | Help, allow, let |
| Subsequent | Next |
| Prior to | Before |
| In the event that | If |
| A number of | Several, many, a few (be specific when possible) |

**Define technical terms on first use.** If a term is necessary (and many are), define it
the first time it appears. Add it to the glossary.

**Keep sentences under 25 words.** Long sentences bury the action. When a sentence
exceeds 25 words, look for a place to split it.

**One idea per sentence.** A sentence that contains "and" twice probably contains three ideas.

**Use active voice.** Active voice names who does the action. Passive voice hides it.

- Active: "The system sends a notification when the document is approved."
- Passive: "A notification is sent when the document has been approved."
- Better: "You receive a notification as soon as a reviewer approves the document."

**Lead with the action.** In instructional content, start sentences with the verb.

- Weak: "In order to publish your documentation, you should click the Publish button."
- Strong: "Click **Publish** to make your documentation live."

### Reading level target

Target a reading level of grade 8 to 10 for end-user documentation. Developer documentation
can be written at a higher level due to the technical audience, but plain language rules
still apply.

Tools that measure reading level: Hemingway Editor, Readable.io.

The Quality Agent checks the Flesch-Kincaid reading level of all generated documentation
and flags content above grade 12.

### What plain language is not

Plain language is not:

- Dumbing down content
- Removing necessary technical detail
- Avoiding precision
- Treating the user as unsophisticated

Plain language is respecting the user's time. Every word that does not help the user
accomplish their goal is a word that wastes their time.

## 10. Second Person Style

### Always write in second person

Address the reader directly as "you." Do not refer to the reader as "the user,"
"one," "they," or "users."

| Avoid | Use instead |
|---|---|
| The user clicks Save | Click **Save** |
| Users can configure notifications | You can configure notifications |
| One must first authenticate | First, authenticate with your API key |
| The administrator should verify | Verify that your settings are saved |

### Why second person works

Second person places the reader inside the action. "Click Save" is an instruction.
"The user clicks Save" is a description of an instruction. Documentation should give
instructions, not describe them.

Second person also removes ambiguity about who the actor is. "The system sends a
notification" is passive. "You receive a notification" is active from the user's perspective.

### Exceptions to second person

Use third person only when describing what the system does, not what the user does:

- "ADUMAS detects the commit and queues it for processing." (system action, third person)
- "Click **Connect** to trigger the detection." (user action, second person)

Do not mix within the same sentence. Write the user's action and the system's response
as two separate sentences.

## 11. Document Types Reference

### Getting Started guide

**Purpose:** Take a new user from zero to their first meaningful success in the product
in the shortest path possible.

**Length:** Short. A Getting Started guide that takes more than 15 minutes to follow
is too long.

**Structure:**

```
# Getting Started with [Product Name]

## What you will accomplish
[One sentence: what the user will be able to do by the end of this guide]

## Before you begin
[Minimum prerequisites only: an account, a browser, a specific role]

## Step 1: [First action toward first value]
## Step 2: [Second action]
## Step 3: [Final action and first moment of value]

## What's next
[2-3 links to next steps based on what the user just accomplished]
```

**Key principle:** The Getting Started guide is not a tour of every feature. It is the
critical path to first value. Include only what is essential to reach that first moment.
Every optional step removed is a user who does not give up before they start.

### Feature reference guide

**Purpose:** Explain what a specific feature does, how to use it, and what options are available.

**Structure:**

```
# [Feature Name]

## Overview
[2-3 sentences: what this feature does and who it is for]

## How it works
[Brief explanation of the mechanism, without implementation detail]

## How to [primary task]
[Task-oriented procedure using the template from Section 5]

## How to [secondary task]
[Additional procedures as needed]

## Options and settings
[Table of all configurable options: name, description, default, allowed values]

## Limitations
[What this feature cannot do; known constraints; plan or tier requirements]

## Troubleshooting
[Common problems and solutions]

## Related topics
[Links to related features, prerequisites, and next steps]
```

### Troubleshooting guide

**Purpose:** Help a user who has encountered an error, unexpected behavior, or failed outcome.

**Structure:**

```
# Troubleshooting [Area or feature]

## Quick fixes to try first
[2-3 most common solutions that resolve most issues]

## [Error message or symptom]
**What it means:** [Plain language explanation]
**Common causes:** [List of reasons this happens]
**Fix:** [Steps to resolve]

## [Next error or symptom]
...

## Still stuck?
[How to contact support; what information to include]
```

**Key principle:** Write troubleshooting headings using the exact text of error messages
or the exact symptom description a user would search for.

### Admin and configuration guide

**Purpose:** Help an administrator set up, configure, or manage the product for their team.

**Structure:**

```
# [Configuration area] Administration Guide

## Overview
[Who manages this and what decisions they control]

## Before you begin
[Required permissions or roles to perform these actions]

## [Configuration task 1]
[Task-oriented procedure]

## [Configuration task 2]
...

## Configuration options reference
[Complete table of all settings with descriptions and defaults]

## Role and permission model
[Table of what each role can and cannot do]

## Audit log events
[List of events recorded for compliance purposes]

## Related topics
```

### API reference

**Purpose:** Give developers the complete, accurate specification of every API endpoint.

This is the one document type where completeness is more important than brevity. Every
endpoint, parameter, response field, error code, and authentication requirement must
be documented.

See `references/architecture.md` for how ADUMAS generates API reference from OpenAPI
specifications automatically.

## 12. Screenshots and Visuals

### When to use screenshots

Screenshots help when:

- The UI element is hard to describe in words
- The user needs to verify they are in the right place before proceeding
- A visual outcome (such as a chart or dashboard) is the confirmation of success

### When screenshots hurt more than they help

Screenshots are a maintenance liability. A screenshot becomes wrong the moment the UI changes.
Outdated screenshots are worse than no screenshots because they actively mislead users.

Do not use screenshots for:

- Simple button clicks (just bold the button name: "Click **Save**")
- Text input fields (describe what to type)
- Settings that will change frequently
- Large sections of UI where only one element is relevant (crop tightly or skip)

### Screenshot guidelines

When screenshots are necessary:

- Crop to show only the relevant area, not the full screen
- Annotate with numbered callouts when more than one element is referenced
- Include alt text for accessibility
- Store screenshots in a `images/` directory next to the documentation file
- Use PNG format at 2x resolution for sharp display on retina screens

### Alternatives to screenshots

Often a description is clearer and more durable than a screenshot:

- Bold the element name: "Click **Export Data**"
- Use a path: "Go to Settings > Integrations > GitHub"
- Use a code block for what to type or copy
- Use a table for comparing options

## 13. Cross-Linking Strategy

### When to link

Link when:

- A concept is introduced that is explained in more detail elsewhere
- A prerequisite is mentioned (link directly to the prerequisite documentation)
- A next step is described at the end of a guide
- A term in the glossary is used for the first time on the page
- An alternate approach to the same goal is documented elsewhere

### When not to link

Do not link when:

- The concept is fully explained inline and the link would be a distraction
- The linked page covers a much broader topic and the user will need to hunt for
  the relevant section (in this case, explain inline)
- You have already linked to the same page in the same section

### Link text rules

Use the destination document title or the specific concept as link text:

| Avoid | Use instead |
|---|---|
| Click here to learn more | See [How to configure GitHub webhooks] |
| See this page | See [Authentication and API keys] |
| More information | [API rate limits and quotas] |
| Read the docs | Review the [Getting Started guide] |

### Bidirectional links

When two documents are related, link from each to the other. A user who arrives
at either document through search should be able to navigate to the other.

The Quality Agent validates that related documents are bidirectionally linked as
part of the automated quality gate.

## 14. Glossary and Terminology Management

### Why consistent terminology matters

Inconsistent terminology creates confusion and erodes trust. If the UI calls it
"workspace," documentation calls it "organization," and the API calls it "account,"
users waste time wondering if they are the same thing.

### The terminology standard

For each product concept, define:

- **Canonical term:** The exact word or phrase to use in documentation
- **Definition:** One sentence explaining what it means
- **Do not use:** Synonyms to avoid
- **Note:** Any edge cases or context-specific usage

Maintain this in a `GLOSSARY.md` file at the root of the documentation repository.

### Enforcing terminology

The Quality Agent checks all generated documentation against the product glossary
before publishing. It flags uses of "do not use" synonyms and suggests the canonical term.

### Capitalization conventions

Product feature names are capitalized when referring to the feature specifically
("the Documentation Generator Agent"). Common nouns derived from feature names are
lowercase ("the generated documentation," "a documentation draft").

When in doubt: if you can replace the word with a common noun and the sentence still
makes sense, lowercase it.

## 15. Analytics and Continuous Improvement

### What to measure

Documentation quality is not subjective. Measure it:

**Search behavior:**

- Queries with no results: gaps in coverage
- High-volume queries with high bounce rate: content that does not answer the question
- Queries that land on the Getting Started guide but lead to immediate exit: getting
  started guide is not matching user expectations

**Page engagement:**

- Pages with very high time-on-page: content may be unclear or too long
- Pages with very low time-on-page: content may not be what the user expected (or
  they found the answer immediately, which is a success)
- Pages with high exit rate at a specific section: that section is where users give up

**Support ticket correlation:**

- Track which support tickets reference a documentation gap
- Which features generate the most "how do I" tickets? Those features need better documentation.
- When a support ticket is resolved with a documentation link, that link should be
  added to the relevant documentation as a cross-link

**User ratings:**

- Add a simple "Was this page helpful? Yes / No" at the bottom of every page
- Pages consistently rated "No" are priority for improvement
- Collect optional comments from "No" ratings to identify specific gaps

### The improvement feedback loop

```
Search gap analysis (monthly)
         |
         v
Identify top 10 missing topics
         |
         v
Queue documentation generation via ADUMAS
         |
         v
Human review and publication
         |
         v
Track search volume for new pages
         |
         v
Confirm gap is filled; repeat
```

### Support ticket correlation workflow

1. Support agent resolves a ticket
2. Agent tags the ticket with the relevant product area and documentation status
   (exists / missing / inaccurate / found but not helpful)
3. Weekly: review "missing" and "inaccurate" tags
4. Trigger documentation generation or update for top-tagged areas
5. Add the documentation link to the support reply template for that ticket category

### Documentation health score

Track a documentation health score per product area:

```
Health Score = (Pages Current / Total Pages) * 0.4
             + (Helpful Ratings / Total Ratings) * 0.3
             + (Search Hit Rate / Total Searches) * 0.3
```

A health score below 0.6 triggers a review. A health score above 0.8 is target state.

## 16. The Five-Persona Writing Model

The best documentation reads as if a full cross-functional team wrote it together.
No single person has all the perspectives needed to produce complete, accurate, usable documentation:

- A product manager understands user goals but may miss technical edge cases.
- A technical writer structures content well but may not know which errors are common.
- A support engineer knows the failure modes but may not explain the happy path well.
- A QA engineer knows the edge cases but may not write for readability.
- A developer knows the technical accuracy but may write at too high a level for the audience.

ADUMAS applies all five perspectives to every documentation artifact via sequential review passes.
Use this framework when reviewing AI-generated documentation or writing from scratch.

### The Five-Persona Review Checklist

Before approving any documentation, run through these five lenses:

**Product Manager lens - Is the "why" present?**
- [ ] The opening sentence explains what the user will accomplish and why it matters
- [ ] The guide is oriented around the user's goal, not the system's structure
- [ ] Success criteria are implicit in the outcome statement ("You have now [goal]")
- [ ] The scope is appropriate - not too broad, not too narrow

**Technical Writer lens - Is the structure sound?**
- [ ] Headings are descriptive and action-oriented
- [ ] Steps are numbered in the correct sequence
- [ ] Each step is one action only
- [ ] Prerequisites are listed before steps begin
- [ ] There is an outcome statement at the end
- [ ] Content is written in second person ("you")
- [ ] Plain language throughout; no unexplained jargon

**Support Engineer lens - Are the failure modes covered?**
- [ ] The most common errors are documented with their exact error messages
- [ ] Each error has a plain-language explanation and a fix
- [ ] A "Still stuck?" section points users to the next escalation path
- [ ] The guide does not assume the happy path is the only path

**QA Engineer lens - Are the edge cases covered?**
- [ ] Known limitations are stated
- [ ] Prerequisites include all conditions that must be true before starting
- [ ] The guide handles the case where a step produces an unexpected result
- [ ] Permissions and role requirements are explicitly stated
- [ ] Feature availability (plan, edition, region) is noted where relevant

**Developer lens - Is the technical accuracy verified?**
- [ ] API parameters match the current API specification
- [ ] Code examples are correct and runnable
- [ ] UI element names match the current interface
- [ ] Version-specific behavior is noted where applicable
- [ ] The guide was verified against the current codebase state, not the spec

### Applying the Model When Reviewing AI Output

When reviewing a draft from the Documentation Generator Agent:

1. Read the draft once without marking anything.
2. Apply each persona's checklist. Mark each failure with the persona initials (PM, TW, SE, QE, Dev).
3. If fewer than three persona checklists have failures, edit inline and approve.
4. If three or more persona checklists have failures, reject and regenerate with a more specific prompt targeting the failing dimensions.

This is faster than freeform editing and produces more consistent documentation quality across reviewers.

### The five most important rules

1. **Second person, always.** Write "you," not "the user."
2. **Task-oriented, always.** Every section helps the reader do something.

## Section 18: Healthcare and Clinical Trial Documentation

Documentation for clinical trial management systems requires additional care beyond
standard software documentation. This section covers PHI-awareness, regulatory context,
clinical terminology, and audit trail documentation.

### PHI-Aware Writing

Protected Health Information (PHI) must never appear in generated documentation. This
applies to examples, screenshots, code samples, and any illustrative data.

**Rules for all documentation generated from clinical systems:**

- Use synthetic placeholder values in all examples: "Patient #1042", "Jane D.", "Study ABC-001", "Site 01"
- Never use real patient names, dates of birth, medical record numbers, or study IDs
- Never embed real data from the system in generated documentation
- Screenshot instructions must specify: "Use test data, not real patient data, for screenshots"

**PHI sensitivity notice.** Include this block at the top of any guide that involves patient data:

```markdown
> **Data sensitivity.** This module contains protected health information (PHI).
> Access is logged and audited. Do not share screenshots or exports outside of
> authorized channels.
```

### Regulatory Context

Clinical trial management systems operate under regulatory frameworks that affect
what must be documented and how.

**ICH E6(R2) GCP (Good Clinical Practice).** Requires audit trails for all data
entered or modified in a clinical trial system. Any module that logs user actions
(creation, modification, deletion of records) must include documentation covering:

- What actions are logged
- How long logs are retained
- Who can view logs
- How to export logs for regulatory inspection

**21 CFR Part 11.** US FDA requirement for electronic records in clinical trials.
Systems subject to Part 11 must document:

- User authentication requirements
- Electronic signature workflows
- Audit trail access and content
- System access controls and who manages them

If the system is HIPAA-covered, include a HIPAA section in the admin guide covering:
access controls, audit log review procedures, and breach response steps.

### Clinical Terminology Standards

Use terms exactly as they appear in the system's interface and PRDs. Clinical
terminology is precise and regulated. Do not paraphrase.

| Write this | Not this |
|---|---|
| Investigational medicinal product (IMP) | Drug, medicine, medication |
| Disposition | Removal, use |
| Protocol | Study plan, trial plan |
| Participant or subject | Patient (unless the system uses "patient") |
| Adverse event | Side effect, reaction |
| Visit | Appointment (unless the system uses "appointment") |
| Site | Clinic, hospital, location |

The system's CLAUDE.md, i18n files, and PRDs are the authoritative source for
correct terminology. Use them. If a term in the code differs from a term in the PRD,
flag it in the gap report and use the PRD term in documentation.

### Role-Gated Documentation

Clinical trial systems have complex permission models. Do not document features in
a guide for an audience that cannot access them.

**Before writing any section, check:**

1. What role is required to perform this action? (Read the Policy file)
2. Is this action scoped to a site, a study, or the global system?
3. Are there actions that look the same but have different permissions? (e.g., "view" vs "view all sites")

**Generate a permissions table for every module:**

| Action | Minimum Role | Scope |
|---|---|---|
| View patient list | Site Staff | Own site only |
| Add a patient | Site Coordinator | Own site only |
| View all sites | Sponsor | Read-only |
| Delete a patient record | Site Admin | Own site only |
| View audit log | Site Admin, Sponsor | Scoped to their access |

### Audit Trail Documentation

Any module that uses activity logging (Spatie ActivityLog in Laravel, or equivalent)
must include an audit trail section. Generate this section by reading the model's
activity log configuration and the audit controller if present.

Template:

```markdown
## Audit trail

Every change to [module name] is logged automatically. The audit trail records:

- Who made the change (user name and role)
- What changed (field name, old value, new value)
- When the change was made (timestamp)
- From which site the change was made

To view the audit trail:

1. Go to [Module] in the main navigation.
2. Click **Audit Log** in the top-right corner.
3. Use the filters to narrow by date range, user, or record.

Audit logs are retained for [X years] in accordance with [regulatory standard].
Contact your system administrator to export logs for regulatory inspection.
```

### Dynamic Forms Documentation

If the system uses a schema-driven form engine (forms table -> elements -> field types),
generate field documentation from the element definitions rather than from hardcoded UI.

**Per-element documentation pattern:**

```markdown
### [Element label]

**Field type:** [text / dropdown / date / checkboxes / ...]
**Required:** [Yes / No]
**Options:** [List values if dropdown or radio]
**Rules:** [Validation constraints from the element config]
**Notes:** [Any conditional logic: "Appears only when [parent field] is [value]"]
```

For tabular elements (L3 forms in the Standard Forms module), document the table
as a section with its own field list. Explain that rows can be added and removed.

### Translatable Content

If the system supports multiple languages (i18n), note in the admin guide which
fields are translatable and how to manage translations. Do not hardcode English
strings in documentation examples - use the i18n key path and the English label
together so the reader can find the field regardless of their language setting.

## Section 19: Anti-Patterns Specific to Healthcare Documentation

| Anti-pattern | What to do instead |
|---|---|
| Real patient data in examples | Always use synthetic placeholder values |
| Undifferentiated guide for all roles | Split by role; check Policy files |
| Documenting a feature behind a feature flag as if it is live | Note "Available when [flag] is enabled" |
| Using generic software terms for clinical concepts | Use the exact clinical term from the PRD or i18n file |
| No PHI notice on patient-facing sections | Add the PHI sensitivity block at the top |
| Audit trail described as optional | Audit trails are mandatory in GCP-regulated systems; say so |
| Screenshots with real study or patient data | Replace with synthetic data or use text descriptions |
| One guide covering all study phases | Split by phase: pre-screening, enrollment, active, completed |

## Section 20: The Book Standard - How Every Manual Must Be Structured

A user manual is a book. Not a reference dump, not a feature list, not a collection of
release notes. A book has chapters that build on each other. Every chapter is
self-contained. A reader can open any chapter and get everything they need without
hunting through other sections.

This section defines the mandatory structure every ADUMAS-generated manual must follow.
Apply it regardless of the product, platform, or audience.

---

### 20.1 The Mandatory Chapter List

Every complete user manual must include these chapters, in this order:

**Chapter 0: About This Manual**
- Who this manual is for (all personas listed)
- How to use this manual (role-specific reading guide)
- How the product is versioned
- Where to get help if the manual does not answer your question

**Chapter 1: What Is [Product Name]?**
- One-paragraph plain-language description of what the product does
- The problem it solves and for whom
- How it fits into the broader platform or workflow
- A "how it all fits together" overview - either a diagram or a numbered narrative of the full workflow from start to finish (e.g. case submission to impact survey)
- Key concepts: define every term a user will encounter, in plain language, before they encounter it

**Chapter 2: Roles and Permissions**
- Every role in the system, defined in plain language
- A permissions matrix: rows = actions, columns = roles, cells = Yes/No/Conditional
- How roles are assigned (by whom, when, under what conditions)
- What a user should do if their role seems wrong

**Chapter 3: Getting Started**
- Prerequisites (access, setup, any configuration required)
- First login or first-time access
- A complete end-to-end walkthrough of the most common first task for the primary persona
- Not a feature tour - a real task, from opening the app to a completed outcome

**Chapter 4+: One chapter per major feature or workflow**
See Section 20.2 for the mandatory structure of each feature chapter.

**Penultimate chapter: Troubleshooting**
See Section 20.4 for mandatory content.

**Final chapter: Reference**
- Glossary of all terms used in the manual
- Limits and constraints table (file sizes, counts, timeouts, etc.)
- System messages and toast notifications index
- Email notifications reference table
- Keyboard shortcuts (if applicable)
- Support and escalation contacts

---

### 20.2 Mandatory Structure of Every Feature Chapter

Every chapter covering a feature or workflow must have all of these sections.
A chapter is not complete if any section is missing.

```
# Chapter N: [Feature Name]

> **Who this chapter is for:** [Persona list]
> **What you will be able to do:** [1-2 sentence outcome statement]
> **Before you start:** [Prerequisites - access, prior steps, required data]

## Overview
One paragraph. What this feature is, why it exists, what problem it solves.
Not a list of sub-features. A narrative that gives context.

## [Core task 1 - imperative heading, e.g. "Create a Case Review"]
### When to use this
### Before you begin
### Steps
(numbered, second person, active voice, each step = one action)
### What happens next
(the outcome - what the user sees, what the system does, what email fires)
### If something goes wrong
(the most common errors and how to resolve them)

## [Core task 2...]
(same structure)

## Best Practices
3-5 specific, actionable recommendations. Not generic advice.
E.g. "Mark a case urgent only when the clinical decision must be made within 24 hours.
Overusing urgency flags reduces their impact on panel prioritisation."

## Limits and Constraints
A table of any limits that apply to this feature specifically.
| Limit | Value | Notes |
|---|---|---|
| Maximum file attachment size | 25 MB | Per file. No limit on number of attachments. |
| Maximum collaborators per case | 10 | Contact your panel owner to request an exception. |

## Reference: System Messages and Toasts
A table of every system-generated message a user will see in this feature.
| Trigger | Message shown | Where shown |
|---|---|---|
| Case assigned | "Case reassigned successfully." | Toast |
| Collaborator accepts | "[Name] accepted the collaborator invitation." | System chat message |

## Related Topics
Links to other chapters this feature connects to.
```

---

### 20.3 Role-Specific Reading Guide

Every manual must include a reading guide at the start (Chapter 0 or as a sidebar/callout).
Users should never have to read chapters that do not apply to them.

Format:

```
## How to use this manual

Find your role below and read the recommended chapters.

| Your role | Start here | Then read |
|---|---|---|
| Clinician (case creator) | Chapter 3 (Getting Started), Chapter 5 (Creating Cases) | Chapter 6 (Case Chat), Chapter 7 (Patient Data Access), Chapter 11 (Impact Survey) |
| Specialist (reviewer) | Chapter 3 (Getting Started), Chapter 5.3 (Accepting Cases) | Chapter 6 (Case Chat), Chapter 7 (Patient Data Access), Chapter 9 (Support Request) |
| Panel Leader | Chapter 4 (Roles), Chapter 8 (Reassigning Cases) | Chapter 10 (Panel Dashboard), Chapter 12 (Impact Summary) |
| Panel Owner | All chapters, starting with Chapter 2 (Roles) | Chapter 13 (Panel Settings - all sections) |
| Administrator | Chapter 2 (Roles), Chapter 15 (Activity Log) | Chapter 14 (Admin Guide) |
```

---

### 20.4 Mandatory Troubleshooting Chapter

The troubleshooting chapter is not an FAQ. It is structured by symptom, not by question.
Every troubleshooting entry has: symptom, likely cause, resolution steps, escalation path.

Required format for each entry:

```
### [Symptom - what the user observes, not what they think caused it]

**You see:** [Exact description of what the user sees]
**Likely cause:** [Plain language explanation]
**To resolve:**
1. [Step]
2. [Step]
**If this does not resolve it:** [Who to contact, what information to provide]
```

Minimum 8 troubleshooting entries per manual. Derive them from:
- Support tickets or known issues (if available)
- Pest feature tests that cover error paths
- Edge cases documented in the PRD or functional requirements
- The "if something goes wrong" subsections in each feature chapter (consolidate here)

---

### 20.5 Glossary Requirements

A glossary must appear as the first section of the Reference chapter.

Rules:
- Define every product-specific term on its first use in the body, AND collect all definitions in the glossary.
- Write definitions for a reader who has never used the product before.
- Do not define a term by using the term itself.
- Sort alphabetically.
- Cross-link related terms with "See also: [Term]".

Example entry:

```
**Panel**
A group of specialists organised around a clinical specialty (e.g. Cardiology, Radiology).
Cases are submitted to panels for expert review. Each panel has its own members, settings,
and access controls. A panel must have at least one Panel Owner. See also: Panel Member,
Panel Leader, Panel Owner.
```

---

### 20.6 Scenario-Based Writing

Every feature chapter must include at least one scenario that grounds the instructions
in a realistic clinical or operational context.

A scenario is not an example input. It is a brief narrative that establishes:
- Who the user is (role + context)
- What situation they are in
- What they need to accomplish
- Why this particular feature is the right tool

Format:

```
> **Scenario:** Dr. Patel is a cardiologist at Site 01. She has reviewed a patient
> with an unusual ECG pattern and wants a second opinion from the Cardiac Imaging panel
> before deciding on the next steps. She needs to create a case review that includes
> the patient's recent ECG form and a clear clinical question.
>
> Follow the steps below to create a case review.
```

The scenario appears at the top of the relevant task section, before the steps.
It is set off in a blockquote so it is visually distinct from the instructions.

---

### 20.7 Limits, Constraints, and System Boundaries Reference

Every manual must include a consolidated limits table in the Reference chapter.
This captures all system constraints so users never discover them by hitting an error.

Derive limits from:
- FormRequest validation rules (max, min, size, mimes validators in Laravel)
- Database column constraints (character limits, nullable vs required)
- Config files (timeout values, SLA thresholds, file size limits)
- Feature tests that assert boundary conditions
- PRD implementation decisions section

Table format:

```
| Feature | Constraint | Value | Notes |
|---|---|---|---|
| File attachments | Maximum file size | 25 MB per file | All formats accepted unless listed |
| File attachments | Blocked file types | .exe, .bat, .sh | Security policy |
| Case collaborators | Maximum per case | 10 | Contact panel owner for exceptions |
| AI summary | Timeout | 30 seconds | Regenerate if it does not appear |
| Panel invitation | Expiry | 7 days | Panel owner can resend expired invitations |
| Case inactivity | Warning threshold | 14 days | Email sent to case creator |
| Case inactivity | Auto-close threshold | 30 days | Cannot be reopened; new case required |
```

---

### 20.8 PHI and Data Privacy Section (Healthcare Platforms)

Any manual for a healthcare or clinical platform must include a dedicated data privacy
section in Chapter 1 or Chapter 2. It is not optional.

Required content:
- What data the product can display and to whom
- What "restricted data" means and who controls access to it
- How data access requests work (who requests, who approves, what is logged)
- Audit trail: what is logged, who can view logs, how long logs are retained
- What users should NOT do (screenshots of patient data, sharing access credentials, etc.)
- Who to contact if a data access issue occurs

Format this as a dedicated section with a prominent callout:

```
> **Data sensitivity notice.** [Product name] displays protected health information (PHI).
> All actions are logged and audited. Do not share screenshots of patient data outside
> of authorised channels. If you believe data has been accessed inappropriately,
> contact your site administrator immediately.
```

## Section 21: Critique-Proven Rules - What Separates Good from Enterprise-Grade

The rules in this section come directly from real critique feedback on AI-generated
manuals. Each rule was identified as a specific failure mode in production documentation.
Apply every rule to every manual, with no exceptions.

---

### 21.1 Never Use "Chapter" - Use Descriptive Workflow Names

"Chapter" sounds like a printed textbook. SaaS and enterprise documentation uses
descriptive, action-oriented or role-oriented section names.

**Never:**
- Chapter 1: What Is [Product]?
- Chapter 5: Creating a Case Review
- Chapter 12: Support Requests

**Always:** Use names that tell the reader what they will be able to do or understand.

| Academic (never use) | Enterprise (always use) |
|---|---|
| Chapter 0: About This Manual | Introduction |
| Chapter 1: What Is [Product]? | Platform Overview |
| Chapter 2: Roles and Permissions | Roles and Access Control |
| Chapter 3: Getting Started | Getting Started |
| Chapter N: [Feature] | [Feature] Workflow / [Feature] Management / [Feature] Guide |
| Chapter N: Troubleshooting | Troubleshooting |
| Chapter N: Reference | Reference and Appendix |

Use a PART structure to group sections by frequency of use (see Section 21.5).

---

### 21.2 Always Generate Separate Documents for Separate Audiences

A single document that combines user instructions, admin configuration, and system
internals is not a user manual. It is a specification document dressed as one.

**Always produce at minimum two separate documents:**

**Document 1: User Guide**
- For end users performing daily tasks
- Covers: what buttons do, what happens next, common workflows, errors they will see
- Does NOT cover: configuration, admin tools, timeout internals, permission logic,
  assignment algorithms, audit systems, dashboard analytics

**Document 2: Admin and Configuration Guide**
- For administrators, panel owners, system operators
- Covers: configuration options, permission management, automation rules,
  timeout settings, audit logs, dashboard analytics, assignment logic
- References the User Guide for end-user workflows rather than repeating them

If the product has a developer audience: a third document covering APIs, webhooks,
and integration configuration.

**The test:** Would a clinician on their first day need to read this section? If no,
it belongs in the Admin Guide, not the User Guide.

---

### 21.3 Never Let Internal Field Names Appear in User Documentation

Internal field names from the database, code, or configuration are never appropriate
in user-facing documentation. They create cognitive load, expose implementation details,
and signal that the document was written from code rather than from the user's perspective.

**Never write:**
- "If `prevent_non_matched_specialty` is enabled..."
- "The `published_at` timestamp is set when..."
- "The `timeout_urgent_hrs` value controls..."
- "The `consultant_id` field stores..."
- "Set `allow_any_specialty_case` to true..."

**Always translate to plain language:**
- "If the panel is configured to restrict cases to matching specialties..."
- "When the panel is published..."
- "The timeout period for urgent cases is configured in Panel Settings..."
- "The assigned specialist is..."
- "To allow cases from any specialty..."

**The rule:** If a user would need to open a database client or read code to understand
the term, rewrite it. The user guide has zero technical identifiers. The admin guide
may have field names only in configuration reference tables, clearly labelled as such.

---

### 21.4 Lock Terminology Before Writing - One Noun Per Concept

Inconsistent terminology is one of the most damaging quality problems in documentation.
When the same thing is called "Case", "Consult", "Review", and "Consultation" in different
sections, users lose confidence and search fails.

**Before writing any section:**

1. Identify every key concept in the product.
2. Choose ONE term for each concept. Use the term the user sees in the UI.
3. Document the chosen terms in the glossary first.
4. Use only those terms throughout. No synonyms, no variation.

**Terminology lock table (example):**

| Concept | Chosen term | Never use |
|---|---|---|
| A clinical consultation request | Case | Consult, Review, Consultation, Request |
| The person submitting the case | Clinician | Creator, Submitter, Requester |
| The person reviewing the case | Specialist | Reviewer, Consultant, Assignee (in user-facing text) |
| The unique identifier | Case ID | Review ID, Consult ID, Reference |

Write the terminology lock table before the first section. If you find yourself reaching
for a synonym, the terminology is not locked properly.

---

### 21.5 Structure by Frequency of Use - Daily Tasks Before Edge Cases

Information architecture by frequency of use determines whether a user can find what
they need in under 30 seconds. Always structure the document in this order:

**PART 1 - Introduction**
Everything a new user needs to get oriented: what the product is, quick start,
roles and access. Maximum 3 sections. Minimum words.

**PART 2 - Daily Workflows**
The tasks a user performs every day or every week. These sections are the most read,
must be the clearest, and must be first after the introduction. No admin content here.

**PART 3 - Operational Features**
Features used regularly but not daily: configuration tasks the admin performs weekly,
panel management, notifications settings.

**PART 4 - Analytics and Administration**
Dashboards, reports, audit logs, and system configuration. This is where admin-only
content lives. Users who do not have admin access skip this section entirely.

**PART 5 - Troubleshooting and Reference**
Troubleshooting (symptom-structured), glossary, limits table, system messages index,
notifications reference. This is looked up, not read sequentially.

**The test:** Could a new user on their first day skip PART 4 entirely and still use
the product effectively? If not, something in PART 4 belongs in PART 2.

---

### 21.6 Always Include a Quick Start Near the Top

A Quick Start section is not optional. It is the single most impactful addition to
any user manual. Users who cannot accomplish their first task in under five minutes
stop reading the manual and start asking colleagues.

The Quick Start appears immediately after the Introduction, before any detailed sections.
It is numbered steps only - no explanations, no prerequisites, no error states.
Those belong in the detailed sections that follow.

**Format:**

```markdown
## Quick Start

Get to your first result in under 5 minutes. Detailed instructions for each step
are in the sections below.

### For [Primary Persona - e.g. Clinicians]

1. Click [Product Name] in the main navigation.
2. Click **[Primary Action]**.
3. Search for and select the patient.
4. Enter your clinical question.
5. Click **Submit**.

Your case is now open and the panel has been notified.

### For [Secondary Persona - e.g. Specialists]

1. Click [Product Name] in the main navigation.
2. Open **[Inbox View]**.
3. Click a case to open it.
4. Click **Accept** to take responsibility for the review.
5. Reply in the chat with your assessment.
```

Keep the Quick Start to 10 steps or fewer per persona. If a workflow cannot be
summarised in 10 steps, it is not a Quick Start - it is a workflow guide. Write both.

---

### 21.7 Keep Standard UX Patterns Brief

Not every feature requires a full task block. Standard UX interactions that users
encounter in every SaaS product should be documented briefly, not exhaustively.

**Over-document these:** (they have meaningful product-specific behavior)
- Permission-gated actions
- Multi-step workflows with branching paths
- Actions with irreversible consequences
- Actions that trigger notifications or emails

**Document briefly:** (one or two sentences each)
- Typing indicators
- Message like / reaction buttons
- Draft auto-save
- Pagination and "load more"
- Standard date pickers, dropdowns, search bars
- Toast notifications for common success states

**The test:** Does this feature work differently in this product than it does in Gmail,
Slack, or Notion? If no, one sentence is enough. If yes, write the full task block.

---

### 21.8 Keep Implementation Details Out of User Documentation

The following content belongs in developer documentation or admin guides, never in
user-facing manuals:

**Never include in a User Guide:**
- Email subject line templates with placeholders (`Reminder - Case [ID] inactive for 14 days`)
- API endpoints or HTTP methods
- Database field names or column references
- Cache durations or S3 URL expiry times
- Template engine mentions (MJML, Blade, Handlebars)
- Internal flag names or feature toggle identifiers
- Cron job schedules or background job names
- Deployment environment specifics

**The rule:** If the content requires knowing how the system is built rather than how
to use it, it does not belong in the User Guide. Move it to the Admin Guide under a
"How it works" or "Configuration reference" section, clearly scoped to administrators.

### 21.9 Tone: Direct, Not Formal

Enterprise documentation is clear and direct. It is not formal, legal, or academic.
Formal tone creates distance between the user and the task. Clear tone gets them there faster.

**Replace these patterns immediately:**

| Formal / technical (never use) | Direct / clear (always use) |
|---|---|
| "The collaborator invitation expires at the same timeout horizon." | "Collaborator invitations expire after the case timeout period." |
| "The system will process the request in an asynchronous manner." | "The request may take a few seconds to process." |
| "Users with insufficient privileges will receive an error." | "If you see an access error, contact your administrator." |
| "The aforementioned fields are required prior to submission." | "Fill in all required fields before submitting." |
| "In the event that no reviewer has been assigned..." | "If no reviewer has been assigned..." |
| "It should be noted that..." | (Delete this phrase. Say the thing.) |
| "Please be advised that..." | (Delete this phrase. Say the thing.) |

**The tone test:** Read the sentence out loud. If you would not say it in a conversation
with a colleague, rewrite it.

### 21.10 Visual Hierarchy in Markdown

Text-heavy documentation loses readers. Use visual hierarchy to break up instruction
blocks and draw attention to important information.

**Callout blocks** (use sparingly - maximum 2 per section):

```markdown
> **Note:** You can change this setting later from Panel Settings.

> **Important:** Removing a member is immediate and cannot be undone.

> **Data sensitivity:** This section contains protected health information (PHI).
> All actions are logged and audited.
```

**When to use bold:** Only for UI element names (button labels, field names, tab names)
and the first mention of a defined term. Never for emphasis. Never in step instructions.

**Tables over lists:** When comparing options, roles, or states, use a table.
When listing steps, use a numbered list. When listing items with no order, use bullets
sparingly - if there are more than 5 bullet points, consider whether a table is clearer.

**Status and workflow diagrams:** For any feature with more than 3 states, include a
simple state diagram in Markdown:

```
Open -> Accepted -> In Progress -> Closed
  |                     |
  v                     v
Rejected            Cancelled
```

This takes three lines and eliminates two paragraphs of prose explanation.
