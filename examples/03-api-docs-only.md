# Example 3: API-First Company - OpenAPI-Driven, Developer Audience Only

## Context

A 15-engineer API-first company building a payment processing API. They have:
- A single GitHub repo with a Python FastAPI backend
- OpenAPI 3.1 spec auto-generated from code annotations
- Developer customers who consume the API directly (no UI product)
- An existing Stripe-style documentation portal (built on Docusaurus)
- No Notion, no Confluence, no Jira - GitHub Issues for everything
- One developer advocate who writes documentation manually today

Their pain: every time an API endpoint changes, the documentation is out of date within hours. External developers hit incorrect documentation and file GitHub issues. The developer advocate cannot keep up.

---

## What They Asked Claude

```
We're an API company. Our only users are developers.
We have a FastAPI backend with auto-generated OpenAPI spec.
Our docs portal is Docusaurus, hosted on GitHub Pages.

We only need API documentation - no user manuals, no admin guides.
How do we auto-generate and keep the API docs always current?
Which MCPs do we actually need?
```

## What the Skill Produces

### Recommended Architecture (API-Docs-Only Variant)

This is a simplified, focused pipeline. No Knowledge Graph, no Audience Adapter (audience is always "developer"), no Notion or Confluence.

```
FastAPI repo (GitHub)
     ↓ [on PR merge or tag push]
GitHub MCP → read openapi.json from repo
     ↓
API Schema Extractor (skill module)
→ parse endpoints, parameters, request/response models, auth, errors
     ↓
Documentation Generator (developer persona only)
→ generates MDX pages: endpoint reference, code examples, error codes
     ↓
GitHub Actions → commit MDX files to docs/ branch
     ↓
Docusaurus rebuild → GitHub Pages deploy
     ↓
GitHub Issues (auto-created for breaking changes)
```

**What's deliberately excluded:**
- Notion, Confluence, Slack MCPs - not used by this team
- Neo4j - one repo, no cross-service relationships to map
- Audience Adapter - single audience (developers)
- Quality Agent (Phase 2) - start simpler

### The Two-Source Approach

API documentation has two sources of truth, and both must be used:

| Source | What It Provides | Captured By |
|---|---|---|
| OpenAPI spec (`openapi.json`) | Endpoint paths, parameters, request/response schemas, auth requirements, status codes | API Schema Extractor skill module |
| Code comments + docstrings | Business logic, rate limits, edge cases, deprecation notices, "why" context | Codebase Analyst Agent (targeted scan) |

The Generator combines both. The OpenAPI spec provides the structure; the docstrings provide the explanatory depth that makes the documentation actually useful.

### Docusaurus Integration

The pipeline does not replace Docusaurus - it populates it. Generated MDX files are committed to the `docs/` directory in the GitHub repo, and Docusaurus rebuilds automatically via GitHub Actions.

```
repo/
├── src/                       ← FastAPI application code
├── openapi.json               ← Auto-generated by FastAPI on startup
└── docs/
    ├── docusaurus.config.js
    ├── sidebars.js
    └── api-reference/
        ├── authentication.mdx   ← Generated by pipeline
        ├── payments.mdx         ← Generated by pipeline
        ├── refunds.mdx          ← Generated by pipeline
        ├── webhooks.mdx         ← Generated by pipeline
        └── errors.mdx           ← Generated by pipeline
```

The pipeline writes MDX to `docs/api-reference/`, commits with message `docs: auto-update API reference [commit SHA]`, and GitHub Actions handles the Docusaurus build and GitHub Pages deploy.

### Breaking Change Detection

Breaking API changes need special treatment - external developers have already built integrations based on the old behavior. On every PR:

1. Compare `openapi.json` (new) against `openapi.json` (previous commit).
2. Classify changes:
   - **Non-breaking:** new optional parameter, new endpoint, new response field.
   - **Breaking:** removed endpoint, removed required parameter, changed parameter type, changed response schema, new required parameter.
3. On breaking change detected:
   - Generate a migration guide section in the docs.
   - Open a GitHub Issue labeled `breaking-change` with the diff summary.
   - Add a `⚠️ Breaking Change` callout block to the affected endpoint documentation.
   - Set `x-deprecation-date` in the OpenAPI spec (if following a deprecation policy).

### MCPs Needed (Only Two)

| MCP | Purpose |
|---|---|
| **GitHub MCP** | Read `openapi.json` from repo, open issues for breaking changes, commit generated MDX back to the docs branch |
| **Figma MCP** (optional, Phase 2) | Extract UI flow annotations if a dashboard UI is added in the future |

Do not connect: Notion, Confluence, Slack, Jira, Linear. They are not used by this team.

### Code Example Generation

Developer documentation is only useful if it includes code examples. The Generator Agent should produce examples in the languages your developers actually use. For a payment API, that is typically:

```markdown
## Create a Payment

### Request

POST /v1/payments

**Parameters:**

| Name | Type | Required | Description |
|---|---|---|---|
| amount | integer | ✅ | Amount in cents (e.g., 1000 = $10.00) |
| currency | string | ✅ | ISO 4217 currency code (e.g., "usd") |
| customer_id | string | ✅ | The customer ID from a prior Create Customer call |

### Code Examples

\`\`\`python
import acme_payments

client = acme_payments.Client(api_key="sk_live_...")

payment = client.payments.create(
    amount=1000,
    currency="usd",
    customer_id="cus_abc123"
)
print(payment.id)  # pay_xyz789
\`\`\`

\`\`\`javascript
const AcmePayments = require('acme-payments');
const client = new AcmePayments({ apiKey: 'sk_live_...' });

const payment = await client.payments.create({
  amount: 1000,
  currency: 'usd',
  customerId: 'cus_abc123'
});
console.log(payment.id); // pay_xyz789
\`\`\`
```

The Generator Agent must be prompted to produce code examples in at minimum 2–3 languages. Specify the languages in the system prompt: "Always include code examples in Python, JavaScript/Node.js, and cURL."

## Key Decisions Made

**Docusaurus over a new portal.** The team already has a Docusaurus portal that external developers know and bookmark. Replacing it with a new portal would break inbound links and confuse existing users. The pipeline writes into Docusaurus, not alongside it.

**GitHub Actions over a separate deployment pipeline.** The pipeline commits MDX to a docs branch and GitHub Actions handles the rest. This means zero new deployment infrastructure - the existing GitHub Pages setup continues to work.

**GitHub Issues over Jira or Linear.** External developers already file bugs via GitHub Issues. Using GitHub Issues for breaking change alerts means the developer advocate sees documentation gaps alongside external developer feedback - in one place, using a tool the team already checks.

**No Audience Adapter.** The audience is always "developer" - someone building an integration with the API. There is no simplified "end user" guide to generate. The Audience Adapter agent adds complexity with no benefit for this use case.

---

## What to Watch Out For

**OpenAPI spec drift.** FastAPI generates the OpenAPI spec dynamically (on startup). If the spec is not committed to the repo on every PR, the pipeline can't diff it. Add a CI step that runs the app, exports `openapi.json`, and fails the PR if the committed spec differs from the generated one.

**Generated code example accuracy.** The LLM will generate code examples that look plausible but may not work if the SDK naming conventions differ from the API spec naming. Run a code validation step: parse the generated examples and verify that all field names and types match the OpenAPI spec. Flag mismatches for human review.

**Changelog for external developers.** External developers subscribe to API changelogs. Auto-generate a `CHANGELOG.md` in the repo root that tracks all API changes (breaking and non-breaking) by version. Publish this as an RSS feed via the Docusaurus blog plugin.

**Deprecation lifecycle.** When an endpoint is marked for deprecation, the pipeline should: (1) add a deprecation notice to the docs, (2) set `deprecated: true` in the OpenAPI spec, and (3) schedule a GitHub Issue to remind the team to remove the endpoint on the announced deprecation date.
